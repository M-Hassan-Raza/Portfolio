The best code I ever deleted was a utility function called `format_response`. It accepted a response object, a format string, a fallback value, an optional transformer function, and a boolean for whether to strip whitespace. It was used in one place.

I wrote it because I thought I'd need it again, and I never did. It sat in `utils.py` for eight months, collecting type: ignore comments and confusing every developer who opened the file.

This post is about the abstractions I built too early and the DRY violations that would have been better left wet.

---
## The Generic Service Layer That Served Nobody

Early in Polaris, I built a "generic" service layer. The idea was that every model gets a service class with standard CRUD operations, validation hooks, and permission checks, written once and inherited everywhere.

```python
class BaseService:
    model = None
    serializer = None

    def create(self, data, **kwargs):
        self._validate(data)
        self._check_permissions(kwargs.get('user'))
        instance = self.model.objects.create(**data)
        self._post_create(instance)
        return instance

    def _validate(self, data):
        pass  # Override in subclass

    def _check_permissions(self, user):
        pass  # Override in subclass

    def _post_create(self, instance):
        pass  # Override in subclass
```

Every subclass overrode every method. `ProductService._validate` had nothing in common with `CustomerService._validate`. The "shared" base class was an empty method contract that added indirection without reducing duplication.

When I needed behavior that didn't fit the create/read/update/delete pattern, like Polaris's FIFO inventory consumption or double-entry ledger operations, the service layer fought me. It assumed every operation was CRUD, and financial operations aren't.

### What Replaced It

I replaced it with individual service classes and no shared base. `LedgerService` has `credit_customer` and `reverse`. `InventoryService` has `consume_inventory` and `receive_batch`. They share nothing because they do nothing in common.

By DRY standards the code is "less clean", and it's much easier to understand and modify.

## Django Signals for Everything

The [performance log](/blog/optimizing-django-performance/) covers what signals did to Polaris's speed. Debugging them was worse.

At one point, creating a sale in Polaris triggered a chain like this:

1. `post_save` on `Sale` → update inventory
2. `post_save` on `Product` (from #1) → recalculate stock alerts
3. `post_save` on `StockAlert` (from #2) → notify supplier
4. `post_save` on `Sale` (again) → update customer balance
5. Custom signal `balance_changed` → invalidate cached reports

Good luck tracing a bug through that. There's no call stack and no explicit invocation. `grep` finds the handler but not what triggers it, because signals are implicit coupling disguised as decoupling.

### What Replaced It

I replaced them with explicit function calls.

```python
class SaleService:
    def complete_sale(self, sale):
        with transaction.atomic():
            self._deduct_inventory(sale)
            self._update_customer_balance(sale)
            self._invalidate_reports(sale.customer_id)
```

By separation-of-concerns standards this is "worse", since `SaleService` now knows about inventory and reporting. But anyone reading `complete_sale` can trace the whole execution path without leaving the function, and I'll take that over architectural purity.

### When Signals Make Sense

Signals belong at app boundaries where loose coupling matters. Your `billing` app doesn't need to know about your `analytics` app, so a "payment completed" signal is fine when the handler lives in a different bounded context.

Inside a single app's core business logic, they mostly serve the architecture diagram.

## The "Reusable" Component Library

In a frontend project, I built a component library before I had components to put in it: a `BaseCard` with 12 props, and a `BaseButton` with configurable size, variant, icon position, loading state, and disabled tooltip.

`BaseCard` was used in 3 places across the project, each with a completely different layout that made the "base" props irrelevant. Two of the three instances passed so many overrides that the component was essentially a `<div>` with extra steps.

The button was worse. I added a `tooltipPosition` prop because one button needed a left-aligned tooltip. Now every button in the system carries tooltip positioning logic it doesn't use. The component API grew to accommodate every edge case, which meant every consumer had to understand the whole API when all they wanted was a button.

### What I Do Now

I start with the raw HTML elements, and I only extract the shared part once I have three similar components with non-trivial logic in common.

```vue
<!-- Three similar buttons? Copy-paste is fine until it isn't. -->
<button class="btn-primary" @click="save">Save</button>
<button class="btn-primary" @click="submit">Submit</button>
<button class="btn-primary" :disabled="loading" @click="confirm">
  {{ loading ? 'Confirming...' : 'Confirm' }}
</button>
```

The third button has a loading state. That's one button, and no reason for a component library.

## The Config-Driven Architecture

At one point, I tried to make Polaris "configurable" by externalizing business rules into configuration objects:

```python
INVENTORY_CONFIG = {
    "costing_method": "fifo",
    "allow_negative_stock": False,
    "reorder_threshold_multiplier": 1.5,
    "batch_tracking_enabled": True,
    "auto_reorder_enabled": False,
}
```

The idea was that different clients could customize behavior without code changes. Just update the config!

Every "configuration" eventually needed code changes anyway. "Allow negative stock" sounds like a boolean, but the business logic for negative stock is very different from positive-stock-only logic. It needs its own code path, with its own validation, reporting, and financial implications.

I ended up with code riddled with `if settings.INVENTORY_CONFIG["allow_negative_stock"]:` branches, each one tested independently and each one a possible bug. The config took the complexity and spread it across every function that read it.

### What Replaced It

I went back to hard-coded business rules that match the client's requirements. When a new client needs different behavior, I work out whether it's a real variation or a different product. Usually it's a different product.

Configuration is for deployment parameters: database URLs, API keys, feature flags for A/B tests. Business rules are code. They deserve tests, type checking, and code review, none of which work well on a dict of settings.

## The Pattern I Keep Coming Back To

Every abstraction I regret was built for a need I only expected to have. The generic service layer was for "when we have 50 models." The config-driven architecture was for "when we have multiple clients." The component library was for "when we have a design system."

None of those futures arrived the way I imagined, and when they arrived at all, the requirements were different enough that the abstraction didn't fit.

The abstractions I don't regret were all extracted from code that already existed. I wrote the code three times, noticed the pattern, and pulled it out. `TenantAwareQuerySet` in Polaris started as copy-pasted `.filter(organization=org)` calls. When I had 15 models all doing the same filter, the abstraction was obvious and correct.

My rule now is that if you can't point to three existing call sites that would use the abstraction, you're speculating. Speculation in code is expensive because it's permanent until someone is brave enough to delete it.

And deleting abstractions is harder than deleting regular code. Regular code has no dependents. An abstraction has consumers, each of which was shaped by the abstraction's API. Removing it means refactoring every consumer, so it tends to stay.

So when you're about to create `BaseService`, `GenericHandler`, or `AbstractProcessor`, write the specific thing first, and write it again when you need it again. By the third time you'll have seen what the abstraction is.
