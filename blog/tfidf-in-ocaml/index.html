Building a local code search engine in OCaml was a good excuse to learn TF-IDF, pure pipelines, and where immutability helps.

I built Cogitator, a local code search engine in OCaml. It indexes code chunks using TF-IDF, ranks results by cosine similarity, and outputs them as RAG prompts for LLMs. The whole thing is about 500 lines of OCaml.

I picked OCaml because I wanted to learn it, and it happened to suit the problem well.

The Tokenization Pipeline

The core of any search engine is tokenization: turning raw text into searchable terms. In Cogitator, the pipeline is:

raw text → split punctuation → split camelCase → split snake_case → lowercase → stem → remove stopwords

In OCaml, this is a pipeline of pure functions composed with |>:

Each function takes a value and returns a value without mutating anything, so you can read the pipeline top to bottom and know what happens at each step. In Python I would've written this as a series of list comprehensions or a loop with intermediate variables, which works but is harder to follow.

The split_camel function uses character-level pattern matching to detect transitions from lowercase to uppercase:

"getUserName" becomes ["get"; "User"; "Name"]. The recursive go function with accumulator is idiomatic OCaml: a fold over characters, building the result list as it goes.

Most of the TF-IDF computation is folds into OCaml's Map module. Term frequency is a fold over tokens into a StringMap:

Every intermediate value is immutable. The StringMap.add call returns a new map and leaves the old one untouched. In Python with dictionaries, you'd mutate in place and hope nobody else holds a reference. Here, immutability is the default and the compiler enforces it.

Fuzzy Matching via Edit Distance

Search queries contain typos. Cogitator handles this with Levenshtein edit distance. If a query term isn't in the IDF vocabulary, it finds the closest match within edit distance 2:

The match from distance to weight reads better than an if/else chain would. After a while with pattern matching, languages without it start to feel clumsy.

What OCaml Gave Me

Exhaustive matching

The file_kind type is a variant:

Every match on this type has to handle all three cases, so when I added Markdown as a third variant the compiler flagged every function that didn't handle it. In Python, I'd have found those bugs in production.

Composition

The code has no dependency injection, strategy pattern or abstract base classes. The tokenization pipeline is function composition, and search is tokenize → vectorize → cosine similarity → sort. Each piece can be tested in isolation because there are no side effects to mock.

Refactoring

When I changed the search_result type from a tuple to a record, the compiler caught every usage that needed updating. I didn't need to grep for call sites or run the test suite to find what broke.

The library is about 500 lines and covers tokenization, stemming, TF-IDF indexing, cosine similarity search, fuzzy matching, result merging, cache persistence, and a REPL. The same feature set in Python would be noticeably more code, and I'd be less sure it all fit together.

I wouldn't use OCaml for everything. For a data transformation pipeline with a well-defined domain, where correctness matters, it's a very good fit.
